A skincare recommendation engine hosted on AWS.

Built a recommendation engine that takes user-supplied skin type, concerns, and desired outcomes, and returns a ranked set of suitable skincare products — trained on product attribute and review data, served as an API on AWS, and designed around the kind of predictions that actually help a real shopper.

§ Overview

Recommendations that aren't just bestseller lists.

The skincare category is a recommendation problem disguised as a search problem. Most product-finder tools on retailer sites are filters, not recommenders — they narrow the catalog by skin type and let the user sort by bestseller or rating. The actually useful question — given my skin type, my main concerns, and what I'm hoping the product will do, what should I try? — gets buried under filtering noise.

This project was a personal build to understand the full stack of getting a non-trivial recommendation system into a deployed, callable state. The goals:

  • Build a recommendation engine that takes user inputs (skin type, concerns, desired outcomes) and returns a ranked list of products with reasoning.
  • Train the model on a combination of structured product attributes (ingredients, claims, intended skin types) and unstructured review data (what users with similar profiles reported working or not working).
  • Deploy the model as a callable service on AWS — not a notebook output — so that the engineering side of taking a model to production was part of the learning.
  • Build it in a way that would scale to more inputs, more products, and richer signal over time.
§ The Solution

Content-based plus collaborative, served behind a clean API.

The engine combined content-based recommendation (matching user inputs against product attributes) with collaborative signal extracted from review data (what users with similar reported skin profiles found effective), with the two signals combined in a ranking layer.

Data assembly involved gathering and cleaning product attribute data (skin type compatibility, ingredient lists, product category, claims) and review data with user-reported skin context. Significant effort went into normalizing inconsistent ingredient naming and resolving skin-type taxonomy across sources.

The content-based model scored products against user inputs using attribute matching with weighted importance — ingredient compatibility for sensitive-skin users was weighted differently from desired-outcome alignment for users prioritizing specific results.

The collaborative layer used review embeddings to find products that users with similar reported profiles responded well to, providing signal that pure attribute matching missed (a product technically suited to "combination skin" might consistently underperform with users whose other markers matched the input user).

Deployment ran on AWS: model artifacts in S3, inference served via SageMaker endpoints (and Lambda for lighter routing logic), with a clean JSON API that accepted user input payloads and returned ranked product recommendations with reasoning fields per recommendation.

Reasoning surfacing was deliberate — each recommendation came with the top factors driving its rank (ingredient match, desired-outcome alignment, similarity to users with matching skin context). A recommendation without reasoning is just a guess; a recommendation with reasoning is a starting point for the user to decide.

§ Results

A working recommendation API and a clearer sense of where it would go next.

The project delivered a deployed, callable recommendation engine — and, more usefully, a concrete map of where this kind of system gets better and where it stays brittle.

  • End-to-end deployment on AWS with a clean API contract: input payload in, ranked recommendations with reasoning out.
  • Hybrid recommendation logic combining content-based and collaborative signal, with explicit weighting so behavior could be tuned rather than tweaked invisibly.
  • Reasoning fields per recommendation made the system inspectable and built the foundation for explainability that would be required if this ever served real users.
  • A grounded view of the data limits. Review data is messy, self-reported, and skews toward extremes — useful, but not a substitute for real outcome data. The next iteration would integrate explicit feedback loops.
  • Full ownership of the deployment surface area — model training, artifact storage, inference serving, API contract — which made every subsequent ML project I worked on more practical.
